精读笔记

prompt 写得再漂亮，不如给 AI 一双眼睛

这条链接在 X 上被搬运了好几轮——西班牙语版、英文版、中文版、日文版、韩文版我都搜到了，单条阅读量过百万。但推文本身没有内容，它只说了一件事：Claude Code 的作者发布了一支 28 分钟的视频。视频我找到了：27 分 52 秒，Anthropic 官方 session《Mastering Claude Code in 30 minutes》，主讲 Boris Cherny，Claude Code 的创造者兼负责人。X 上那版视频拿不到字幕，所以这篇不是”看完原片”的产物——我找了一份逐句转写（Whisper 转写后人工校订术语）和几份现场听讲报告，交叉核对之后才动笔，有出入的地方下文会标出来。

你有过这种时刻吗

晚上十点，一个需求让 AI 改了七遍。你把 prompt 从两行加到二十行：加上「先思考再回答」，加上「你是一位资深工程师」，加上三条约束，末尾再补一句「不要编造」。回车，结果好了一点，但没到能直接用的程度。你合上电脑，得出一个结论：我大概不太会写 prompt。

这支视频给的诊断完全不一样。它甚至不太谈 prompt 的措辞。

28 分钟里，其实只有一句话

Boris 的履历值得交代一句：前 Meta Instagram 首席工程师，2024 年加入 Anthropic，入职一个月内以 side project 立项 Claude Code，《Programming TypeScript》的作者，自学出身。他在开场就定了调子——不讲历史不讲理论，只讲实操。

而实操讲完，真正立住的判断只有一句：

prompt 写得再漂亮，也不如给 AI 一双能看见结果的眼睛。

他把 Claude Code 定义成”完全 agentic”的工具：不是逐行补全，是交付整个功能、整个文件、整个 bug 修复；它的工具集只有三个——改文件、跑 bash、搜文件，复杂工作靠模型自己把它们串起来。串对了的标志，是它能自己看到串出来的结果。

graph LR A["提问 读懂代码"] --> B["给出计划"] B --> C["你确认"] C --> D["写代码"] D --> E["跑测试或截图"] E --> D E --> F["对验收标准汇报"] style E fill:#fff3cd,stroke:#b8860b,stroke-width:2px style F fill:#d1e7dd,stroke:#198754

这张图是关键：缺了中间那个”跑测试或截图”，写代码那一步就只能靠你在旁边逐行盯。下面五级台阶，都是这一句话的推论。

一级：先问代码，别急着改

他给新用户的第一条建议有点反直觉：不要从写代码开始，先从对着自己的代码库提问开始。Anthropic 内部新人技术 onboarding 就是这么做的，结果是从两三周压到了两三天。

理由有三条。第一，问答阶段没有改文件的风险，却能同时练两件事：你怎么描述问题，以及它对这个项目究竟懂到哪一层。你会慢慢有边界感——什么任务一次能成，什么得来回两三轮。第二，零索引零配置：代码不上传、不建远程库、不用于训练，下载就能用。第三，这类任务容易验真，它答得对不对你自己一眼就知道。

他给的几个问题可以直接抄：”这个类实际是怎么被实例化的？”——它不是做一次文本搜索，而是去找真实的调用点；”这个函数为什么有 15 个参数？”——让它翻 git 历史，看这些参数是哪次提交加的、当时在解决什么、关联了哪个 issue；再比如用 WebFetch 去读 GitHub issue 拿上下文。他自己每周一在站会上都会问一句”我这周 ship 了什么”，让它从 git log 里捞一份清单出来，复制进文档就完事。

二级：动手之前，先要一份计划

一句自然语言就够了，不需要 plan mode 或任何特殊工具：

先头脑风暴几个方案，做个计划，拿给我看，写代码之前先征得我同意。

反例他讲得很实在：有人打开就一句”把这个 3000 行的功能实现了”——有时候一次就对，但有时候做出来的完全不是你想要的。先看一遍计划，通常一分钟就能发现它找错了入口、漏掉了兼容性，或者准备动三十个文件。

计划确认之后再给验收标准。他给的说法是保留现有 API、不引入新依赖、跑完相关测试和类型检查，最后汇报改了哪些文件、还有哪些风险没覆盖。另外他常念的一句咒语是 commit, push, pr：Claude 会自己去看 git log 摸清 commit 格式，建分支、提交、开 PR。这句话短得有点吓人，我在下一节末尾补一句提醒。

三级：给它一双眼睛（最值钱的一级）

这是全场反复强调的机制：当 Claude 有办法检验自己的成果，它就会自己迭代。

手段按领域分。后端和逻辑类用单元测试、集成测试、真实请求结果；Web 前端用 Puppeteer 截图——Anthropic 内部把这套做成了 MCP server 提交进仓库，全队共享，没有哪个工程师需要自己装；移动端用 iOS 模拟器截图；做界面就直接把设计稿图片拖进去，让它对着比。他的原话是：一次能做到不错的水平，迭代两三轮往往就接近完美。

但有个容易漏掉的细节，也是我从转写里特意标出来的一句：要给停止条件。 没有停止条件，它可能在一像素的视觉差异上无限消耗下去。比如”最多迭代三轮，最后汇报仍然不一致的地方”——重点不是这个数字，是让循环有出口。

这也就解释了开头那个痛点。prompt 的措辞只影响第一次输出长什么样，而回路决定了它能不能自己收敛到能用。前者是你在写，后者是它在跑。

四级：把踩过的坑写进 CLAUDE.md

CLAUDE.md 是一个每次会话开头都会被自动读入上下文的 Markdown 文件，Boris 管它叫”项目的记忆”。层级有五层：

层级 位置 用途
企业 企业根目录 全公司强制策略
用户 ~/.claude/CLAUDE.md 个人跨项目偏好
项目 项目根 CLAUDE.md 提交进 git，团队共享
个人 CLAUDE.local.md 不提交，只给自己
子目录 subdir/CLAUDE.md 在该目录干活时才载入

该写什么：常用的 bash 命令、代码风格约定、核心文件的位置、架构决策、MCP 工具的用法。然后他强调了一句：写短。 写长了会白白吃掉一大块上下文，而且通常也没那么有用。

两件容易被忽略的事。一是这套层级不只管记忆文件——斜杠命令、权限白名单与黑名单、MCP server 定义全都按同一套层级走。企业策略里可以把全公司都要跑的测试命令设成自动批准，也可以把某个 URL 永久拉黑、员工无法覆盖。二是记忆能就地写：输入 # 再跟一句话，就当场记进相应的文件，最典型的用法是”这个工具你用错了，以后这样用”；/memory 用来查看和编辑当前载入的所有记忆文件。他的建议是从共享的项目级上下文起步——一个人写一点，全队都受益。

五级：当 Unix 工具用，再谈并行

claude -p "..." 就是 SDK 形态的 CLI：可以传 prompt、限定允许使用的工具、指定 JSON 或流式 JSON 输出。他说 Claude Code 自己就是用这套 SDK 做的，Anthropic 拿它在 CI 和事故响应里跑。用法上要”当一个 Unix 工具想”：git status | claude -p "..." | jq，从对象存储里拉一份巨大的日志喂进去让它找异常，用 Sentry CLI 拉错误让它分析。他自己的判断是这条路才刚刚触到皮毛。

再往上一级才是并行：多开终端 tab、用 tmux 挂住 session、同一个仓库 check out 好几份、用 git worktree 做隔离。

这里有个我觉得比技巧更值得记的地方：他在台上说自己算个”普通用户”，一般一次只跑一个 Claude，最多开几个 tab 对应不同仓库；真正多开的是内外的重度用户。所以并行不是入门必修——前四级跑顺了再谈它，否则你只是把还没验证的改动同时铺开。

顺手抄走的几个快捷键

按键 作用
Shift+Tab 切到自动接受编辑，bash 命令仍然要确认
# 让它记住一件事，写进记忆文件
! 进 bash 模式，命令和输出一起进上下文
@ 把文件或目录拉进上下文
Esc 中断再换方向，适合”二十行里只改一行”的精细修正
Esc Esc 回退到更早的会话节点
Ctrl+R 看完整输出，也就是它在上下文里看到的同一份

几句实在话

一、推文那句话是增长话术。“前 10 分钟超过 300 美元的课程”——视频是 Anthropic 官方免费的 session，内容是从入门到中级的高密度实操，价值在顺序正确、可以照着抄，不在”别人不知道”。同一段文案被翻译成五种语言反复搬运，本身也说明它更适合当入口，而不是当秘籍。

二、这支视频已经过期了一部分。 安装方式当时是 npm，后来官方推荐原生安装器；视频里那个”Claude Code SDK”后来改名成了 Claude Agent SDK；快捷键也随版本变过。照着做之前以官方文档为准。

三、commit, push, pr 有前提。 这种极短指令能成立，靠的是仓库规范清晰、权限和沙箱你信得过。刚上手的仓库，把提交、推送、建 PR 分开确认更稳。

四、它是一场现场分享的录像。 官方标题写的是 30 分钟，实际 27 分 52 秒，结尾还有 Q&A。Q&A 里最坦白的一段是：他觉得实现上最难的是 bash 的安全——既要少弹确认框，又不能让它以意外方式改掉系统状态，最后的解法是只读命令白名单、对命令组合做静态分析，再加一套分层权限；难的地方还在于不是所有人都在容器里跑代码。

从一个闭环开始

如果这 28 分钟只带走一件东西，就带走那张图：先读懂代码 → 要一份计划 → 你确认 → 写代码 → 它自己验证 → 继续改。

一个能自己看见结果的闭环，比二十条 prompt 模板值钱。

具体怎么落地，他也给了最小版本，我建议按这个顺序跑一遍：挑手上一个真实的小需求，先让它把相关代码讲清楚（明确不许改文件）→ 要一份计划并挑一次刺 → 给它一个能验证的手段，哪怕只是”跑这条测试命令”→ 让它自己迭代到通过 → 最后把这次纠错写进 CLAUDE.md。五步一个闭环，跑顺了再谈放权、脚本化和并行。
