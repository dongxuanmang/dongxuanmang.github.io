Agent 精读（十五）：世界不会等你回完话，Agent 也不该只有一个会话

这是《深入理解 AI Agent》精读专题的第十五篇，进入第 6 章「交互：观察与动作空间的扩展」。异步与事件驱动、语音两节精读完，Computer Use 与机器人两节先扫了骨架、留待补读。读的时候手上正好也有两份 2026 年的材料——DeepSeek 十月底开源的 Super-agent 架构，和 Anthropic 的 Claude Tag——放一起对完之后，我发现它们在说同一件事，只是尺度不同。

你有没有遇到过这种时候

Agent 正在跑一个二十分钟的重构。跑到第七分钟，你发现方案选错了。

你只能等。或者更常见的一种：它停下来问你”要继续吗”，而你正在开会；等你看手机的时候，世界已经变了。

第 6 章把这个别扭说得比我想的狠：

在前五章的内容中，Agent 与世界的交互是轮流的。用户说完一句，Agent 想一段、调用几个工具，再回一句；在它思考的这段时间里，世界被默认为静止的。这个前提如此自然，以至于很少被当成一个假设写出来。

这一章把交互拆成两根轴

前五章扩展的是观察空间和动作空间的内容（上下文、记忆、工具、代码）。这一章扩展的是它们的模态和时机：

观察空间的扩展 动作空间的扩展
内容（第 2–5 章） 上下文工程、记忆与知识库 工具、代码生成
模态（本章） 语音、屏幕、物理传感器 说话、点击、关节运动
时机（本章） 世界主动推送、连续流 跨回合、可打断、可抢占

模态这条轴好理解，语音、Computer Use、机器人三节讲的就是它。真正让我停下来的是时机这条轴——因为它把四个相差六个数量级的场景，压到了同一张表上：

秒到天是异步与事件驱动；10 毫秒到 1 秒是语音；亚秒到秒是 Computer Use；毫秒是机器人。

这四个场景看起来毫无关系，但书里的结论是它们共享同一批系统原语。

时机：观察从”我去取”变成”世界推给我”

异步那一节的开头有一句我很喜欢：回合制是模型与接口的一种交互约定，不是环境的性质。

这句话解释了为什么”Agent 主动轮询”这件事从工程上就是错的——不是它慢，是它把接口的假设当成了世界的性质。真实环境不会等模型反应：邮件在它思考时到达，用户在它说到一半时插话，页面在两次截图之间已经变了样。

要接住这些，第一步是把输入统一建模成结构化事件：来源（谁）、渠道（什么方式）、内容（什么）、上下文（跟什么有关）。书里举的例子里，一封客户退款邮件会变成带 priority、customer_tier、related_orders 的 JSON。

第二步才是处理策略。书里按紧急度分三种：

  • 取消式：为紧急事件提前制造一个安全点，立刻停下当前步骤、清空队列、把新事件和紧急事件一起追加进轨迹，重新调模型。
  • 队列式：常规事件进队列，等当前工具返回、轨迹出现一个自然安全点时再一起消费——顺带就实现了批量处理。
  • 并行式：与主任务无关的轻量查询，另起一个推理会话，结果追加回来并标记”与主任务并行”。

然后是我觉得这一节最实用的一句：硬编码的规则判不准语义，书里建议用轻量的分类 LLM 做事件路由器。

五个原语

本章小结把四类交互拍平，收了五个词：唤醒、安全点、取消、抢占、快慢分离。

前四个是工程里非常具体的东西，值得各说一句。

唤醒是”世界能叫醒 Agent”。书里列了三类事件触发工具：定时器（一次性和循环）、后台任务监控（不想让 Agent 盯着命令行烧 token，就让它监控输出里的关键词）、外部事件通道（邮件到达、API 回调、IM 消息）。

书里还顺手批了一个短板：OpenClaw 的 Hooks、Cron、Heartbeat 三种机制里，真正能让 Agent 在没有用户消息时自己动起来的只有 Cron 和 Heartbeat，而它们都是时间驱动的——第三方事件源没有即时通道，只能等下一个周期才察觉。

安全点是”事件只能在某处被合法消费”。同步接口下，这个点出现在一段推理结束、或一次工具返回；原生异步则由系统自己选时机。书里那句提醒挺硬：取消点必须是工具或推理能够安全收尾的位置，未完成的工具结果用显式占位符表示，不能伪造成功。

取消是”停”这件事本身不等于撤销。书里拿 Go 的 ctx.Done() 打比方：收到停止消息只是发了个信号，已经发生的动作不会因此消失。

抢占在毫秒尺度上是必需品——机械臂伸手途中杯子被碰倒，不抢占就来不及。这个原语在软件 Agent 里其实是弱的，后面会说到。

快慢分离是这一章最容易被误读的一个。书里讲的是认知时序：前台模型要在用户还在线时回应，后台模型可以慢慢想。三种方案是取舍不是迭代——快回应慢回答（两个实例各想一遍，容易自相矛盾）、快交互慢提醒（后台给前台递建议，稳定但通信间接）、端到端统一（真正边想边说，但每次升级都要重新训练）。书里对解耦路线给了一个我很认同的工程论证：慢模型迭代时只换后台，不用重训整套实时系统。

把它和 Super-agent 对一遍

读到这里我基本确定：这五个原语，正好是 Super-agent 那篇架构文章的设计清单。 对一遍看：

原语 第 6 章里的形态 Super-agent 的实现 我的判断
唤醒 定时器、心跳、外部事件通道 Trigger：群聊、PR 评论、CI 结果、定时 更强：在模型判断前加了一层程序快筛
安全点 回合边界、推理结束 异步 ReAct：start() 立刻返回，后台结果作为新事件投进会话 一致，只是把安全点从回合末尾挪到了推理步之后
取消 user.interrupt stop 工具；Ticket 结束后工具调用直接被拒 一致
抢占 动作分块被打断 没有显式机制，靠 Router 排队 弱的一环
快慢分离 前台快回应、后台慢推理 程序层快筛、模型层慢判 同名不同物

最后一行是我这篇最想写下来的。书里的快慢分离治的是延迟，Super-agent 的快慢分离治的是成本。 前者是同一个交互里，先给一个能听的回应、再补上想清楚的答案；后者是同一条事件流里，用确定性代码吃掉大部分噪音、把模型留给真正需要判断的少数。同构的只是”分层”，不同构的是”为什么分层”。

中间一行也值得说：书里建议用轻量分类 LLM 当事件路由器，而工程系统在这一层前面又加了一道确定性闸门——来源、群组范围、白名单。差别不在技术，在代价：误唤醒烧掉的不只是 token，还有同事的注意力。

至于抢占为什么弱，我的解释是：软件 Agent 的动作几乎都可逆，回滚一个 PR 比拦住一只机械臂便宜得多。所以这一行原语在软件里被”取消”顶掉了大部分职责。

两套系统其实在解同一类”遗留约定”

第 6 章挑战的是回合制这个约定。Super-agent 那篇挑战的是另一个约定——它那句原话是：Session 应当是系统的实现细节，而不应是用户的认知负担。

两个约定来自同一个地方：它们都是从 LLM API 的形状里长出来的，不是从任务的性质里长出来的。单会话是 API 的调用单位，回合制是 API 的消息单位；等模型能力够了，这两个从技术约束就变成了产品债务。

我读这两份材料时最强的一个感受是：这一代 Agent 系统设计，有相当一部分工作是在把 API 遗留的形状一点点扭回任务本来的形状。

我十月三十一号写过一篇更细的架构拆解，讲它怎么用双层 Router/Worker、Thread 多对多订阅、投机执行的”沉默权”把这些原语落到系统层，这里不再重复：一个人只能同时盯 5 个会话，于是 Agent 被拆成了两层。

Claude Tag 是产品侧的另一个尺度

顺手把 Anthropic 的 Claude Tag 也对了一遍（公测中，形态是 Claude 住在团队的 Slack 里）。它同样把这五个原语用全了，只是尺度小一号：

唤醒靠 routine——定时、盯着某个频道、订阅单个 PR；安全点就是 thread 边界，沙箱一轮释放、下一条消息重建；取消是 thread 里的 Stop 按钮，”停下但保留会话”；快慢分离是平时静默观察、判断要不要插话（快），需要调查才开一个 working session（慢）。

它缺的恰好也是抢占，而且缺得更彻底：thread 之间互不共享状态，所以谈不上谁打断谁。

真正的差别不在原语用没用全，在尺度和授权。尺度上，Claude Tag 是”一个人、一个话题”；Super-agent 是”一个团队、多条任务流”。授权上，前者按频道（静态，进了频道就有频道的权限），后者按请求（每张工单一个授权，动作前再校验一次）。

第 6 章思考题里最该答的一道

第 12 题问：同一个原语在”事件驱动（秒到天）”和”机器人动作分块（毫秒）”两处实现差异由什么决定——环境变化的速度、动作的可逆性，还是观察的获取成本？

我的答案是可逆性，其次才是速度。毫秒尺度上抢占必须做，代价只是动作没做完；秒到天尺度上抢占也能做，但代价从”动作失败”变成了”打断一个人的思路”。所以尺度越小，抢占越重要；尺度越大，取消和安全点越重要——因为大尺度上喊停的是人，人要的是停在一个自己能理解的地方。

顺着这个推下去有一条更实用的结论：软件 Agent 里”取消”比”抢占”重要得多。软件动作大多可逆，大不了回滚；人的注意力不可逆。

我能拿走的三件事

一是设计任何交互，先问时机在谁手里：观察是 Agent 去拉还是世界推来，动作是回合内做完还是跨回合收尾。这两个问题一答，剩下的架构大半就定了。

二是事件入口别只放一个模型。规则快筛在前、模型判断在后，书里给的是后者，工程系统补的是前者。

三是看到”快慢分离”先分清它治的是延迟还是成本，混在一起就会用错——把认知时序的取舍套到事件过滤上，你会以为多加一个模型就能解决噪音。

下一步是第 7 章，评估。这一章我最需要的恰恰是它：上面这些”更强””弱的一环””更彻底”，目前都还没有一个指标接住。
