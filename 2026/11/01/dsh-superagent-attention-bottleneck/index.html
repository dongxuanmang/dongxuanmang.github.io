随笔

一个人只能同时盯 5 个会话，于是 Agent 被拆成了两层

那天晚上，中文科技媒体的标题几乎是同一个模子刻出来的：DeepSeek 重磅开源 Agent 底座架构。

等到翻到原文，它开篇第二句写着：

本文是一篇面向工程实践的架构思路探讨，并非对 DeepSeek Harness 现有产品功能的介绍。

同一件事，信息密度差十倍，情绪差一百倍。这篇笔记写的是原文里那部分信息密度。

原文第二句就写着：这不是产品介绍

先把事实摆正，不然接下来全是误读。

放出来的东西有两样：一篇上万字的架构文章，和一个叫 dsh-superagent-prototype 的仓库（MIT）。README 自己划了边界——研究原型，不是官方产品，可能有 bug，工程风格也可能不一致，用之前自己 review。文章里也交代了，有些设计是未来方向，原型里没实现。

所以这既不是”发布了一个叫 superagent 的产品”，也不是”Agent 的操作系统来了”。它是一个团队把内部跑着的东西写成设计文档，顺手把毛坯房也放了出来。

文章里最硬的证据是一组数字：约 300 条消息、20 个工作请求的模拟环境，每种方案重复 5 次。任务完成时间 p50 是 12.4 分钟、p95 是 15.7 分钟；对照组是”单个会话 + 子 agent 工具”，在”中性提示”下 p95 是 29.5 分钟。

作者自己注明了这是合成负载，衡量的是系统调度与协作能力，不是单个任务干得好不好，”仅作初步参考”。

但这篇文章真正值得读的地方，不是这组数字。

瓶颈挪位了

把这段摘出来：

单任务的上限取决于模型能力，多任务的上限取决于人的注意力。

这是我读完全文后最愿意称之为判词的一句。它敢这么写，是因为一个观察：一个人通常只能同时跟进 3 到 5 个活跃会话。

你回想一下自己：一个终端跑重构，一个窗口查日志，浏览器三个标签分别是文档、issue 和刚发来的需求，中间还要切到群里回一句。多数时候让你手忙脚乱的，是你在做调度，而你的调度带宽只有 3 到 5。

顺着这个判断，他们做了几个决定。下面每个决定，我尽量只说清结论和代价。

拆成两层：一个只说话，一个只干活

第一个决定：把”保持连续”和”并发干活”分成两个角色。

上层叫 Router，常驻，负责接人话、维护全局上下文、派活。关键约束是它不干活——不直接执行具体任务，甚至可以不配 bash 工具。

下层叫 Worker，上下文互相隔离，工具挂满，并发执行。关键约束是它不直接对人说话——推理过程和工具调用不外泄，只向 Router 汇报，由 Router 统一回话。

这个设计有个反直觉的推论，作者自己写了出来：Router 的任务常常没想象中复杂，用轻量模型往往就够；而 Worker 直接决定交付质量，通常要配最强的模型。

读到这里我才反应过来，这套东西省钱的方式不是”用更聪明的模型”，而是”把重活隔离出去”。

还有一句我很喜欢，原文在讲为什么要淡化会话：

Session 应当是系统的实现细节，而不应是用户的认知负担。

常见的 Agent Team 里，主 agent 往往既当项目经理又当主力工程师，推理负载很重。这里反过来，Router 是纯调度。差别不在模型，在谁承担上下文。

副作用：两个 Worker 互相看不见

上下文隔离换来并发，代价是互相失明。

想象一个原文没写、但一定会发生的场景：Worker A 在处理登录超时，改了 session.ts，开了 PR #99；Worker B 在处理 session 模块重构，也改了同一个文件，开了 PR #100。两边都不知道对方存在。

如果靠点对点通信来发现冲突，你会发现无从下手：A 要给 B 发消息，得先知道世界上有个 B，还得知道 B 在改哪个文件。可 A 的上下文是隔离的，它恰好不知道全局有谁。

这是个死结——要通信就得先有全局名册，而全局名册会把隔离省下来的上下文成本又还回去。

他们的解法是换了个方向：不解决”谁该找谁”，改成”谁该关注什么”。

系统里有一条实体叫 Thread，就是一条事件流：一个 PR 底下的所有评论和 CI 结果、一个 IM 话题、一封往来的邮件串。Worker 处理完之后会订阅这条 Thread，之后里面的新消息由程序直接推给它，不再经过 Router。

订阅是多对多的：一条 Thread 可以被多个 Worker 订阅，一个 Worker 也可以订阅多条。

上面那个场景于是变成：B 领活时发现任务和 A 的 PR #99 相关，订了那条 Thread；评审在 #99 上留了一句”别自己写缓存，复用 SessionStore”；这条消息直通给 A 和 B；B 读到之后，发现自己刚把 SessionStore 的接口改了——冲突是它自己发现的，没人通知它。

两个 Worker 全程没给对方发过一条消息，甚至不需要认识对方。

它不传播意图，只传播记录。 这是我从这套机制里抠出来的第一条工程约束：关键决策必须落在共享流里。A 心里决定”标题走 X 方案”却没说出口，B 永远收不到，订阅等于空的。

第二条约束更微妙：看见不等于有权处理。代码里为”上下文”订阅一条 Thread，消息会到，但不带执行权；如果 Worker 发现自己订错了，可以撤销订阅，并把已落到手上的消息连同理由交还回去。

所以它们敢用广播：因为订阅是单向、可撤销、不带授权含义的。噪音的成本，由”随时能退订”来兜底。

能自动建立的订阅才叫架构，要人登记的订阅只是功能。

一条消息该不该管，先过两道闸

订阅解决了”该给谁”，没解决”该不该动”。

接进真实群聊和代码平台之后，事件流是高噪音、低触发率的，绝大多数消息不需要 Agent 介入。每条都调一次大模型，延迟和成本都撑不住。

做法是把计算机系统里的快慢路径搬过来：能用确定代码判的，先用代码判——来源、群组范围、用户或机器人白名单；剩下真正需要语义理解的，才交给模型。程序层是快路径，模型层是慢路径。

这里我想停一下。这套结构最有意思的地方不是新，而是它在别处早就成熟了。

如果你做过客服或工单系统，你会立刻认出这个形状：先规则分流，命中明确的直接走自动化，模糊的、高风险的才升级给人工或大模型。规则吃掉确定性的量，把贵的资源留给不确定性。

但直接照搬会踩坑，中间需要做一层的转换。我把它列成了四条：

客服、工单系统里 这套 Agent 系统里 要转换什么
快路径输出 一个结论：走哪条流程 一个准入：值不值得让模型看一眼 把”规则命中”从决策降格为候选
慢路径是谁 人，不可编程 模型，可编程 给人类的上下文，不等于给模型的上下文
判错代价 转错组，可挽回 会变成一次写操作，不可挽回 必须补一道授权闸门
时间预算 秒级，人在线等 可以等，可以攒 慢路径能做批处理

第三条是分水岭。客服分流错一次，最坏是工单转错部门；这里判错一次”这个请求可以接”，它会用团队账号去改代码。所以它比客服系统多了一整套东西：准入强度、动作前重新校验授权、以及一个 observe 模式——只记录”它本来会做什么”，不真做。

第四条也有意思：客服不能批处理，因为有人在等；这里能批处理，因为它对人的承诺是”结果会来”，不是”立刻回”。

于是有了另一组数字：Trigger 从每分钟 1 条涨到 40 条，平均批处理大小从 1.0 涨到 2.8，单次请求耗时只从 2.5 秒涨到 3.9 秒，于是单个决定分摊的推理时间从 6.4 秒降到 1.6 秒。

越堵越便宜。这在有实时用户在场的系统里做不到。

后台先干，干不出结果就闭嘴

还有一类等待没法批处理：判完了，活还得干，而干活要几分钟到几十分钟。

两个动作。

一个在交互层：把耗时的工具调用改成异步，start() 立刻返回”已启动”，循环不阻塞，后台干完再把结果作为新事件投进来。文章说这个机制已经在 DeepSeek Harness 里实现了，但默认没开。

另一个在判断层，叫投机执行：在还不确定结果会不会被采用的时候，根据环境信号先在后台试。收到会议邀约，先查日程冲突、找背景资料、起草回复；群里有人聊一个 bug，先在后台复现、找修法。

然后是那句让我停顿的规则：只有在确认问题、并且找到简单可行的修法之后才交付；否则全程保持安静。

这句话的分量不在”主动”，在于它给了 Agent 沉默的权利。大多数主动 Agent 的产品逻辑是”我发现了什么，一定要告诉你”，结果主动变成骚扰。这里反过来，找不到价值就不出声。

主动性不只体现在会动，更体现在能忍住不动。

人不在场，它还得活着

前面所有设计都默认系统在跑。那人不在了呢？

传统本地 Agent 把三件事绑在一台机器上：推进循环的计算、需要持久保存的会话状态、以及代码仓库和工具链这些执行环境。设备一休眠，全停。

解法是分两步解绑。第一步把计算和状态分开：计算无状态、可弹性伸缩，状态进数据库。第二步把计算和环境分开：环境留在原地，端侧只装一个轻量 daemon，只执行命令、不保存会话状态。

第二步是我觉得最实用的一条判断——既然难以复制和同步的是环境本身，那就不必让环境跟着计算上云。

然后是看门狗。在主系统外面挂一个独立会话，由定时消息驱动。除了处理接口报错、状态恢复失败这类基础设施问题，它还要判断各个 Worker 有没有实质进展、方向有没有跑偏。

这条我也认同。长期运行的 Agent，最典型的故障不是进程崩了，而是它看起来很忙，其实在原地转圈。光靠进程存活探测，抓不到这种。

Claude Tag 走了另一条路

读完这套东西，我顺手把 Anthropic 的 Claude Tag 又看了一遍。它现在是公测状态，形态是”Claude 住在你的 Slack 里”。

同一个问题的两个答案，放在一起看：

Claude Tag Super-agent
交互面 只有 Slack（频道、thread、私聊） IM、GitHub、邮件都能进
工具面 很广：Drive、GitHub、搜索…… 很窄：通常就一个仓库
会话单位 一个 thread 一个会话，跨 thread 不直接共享状态 Router 一个常驻会话，跨任务共享记忆
执行环境 临时云沙箱，一轮结束就释放 环境留在原地，靠 daemon 接入
授权粒度 按频道，静态 按请求，动作前再校验一次
主动性 在场式：读每条消息，判断要不要插一句 任务式：判断要不要开一张工单
主动的形态 提议、短答、私人建议卡（一天过期） 开 Ticket、派 Worker、跟到 PR

最扎眼的不是技术差异，是方向差异。

Claude Tag 把 AI 塞进人已经在用的工作流，Super-agent 反过来把工作流重构成 AI 的系统、界面退成附属品。一个是渐进渗透，一个是替代式重构。

“主动性”两家都在做，但性质不同。Claude Tag 的主动是”在场式”：读频道里每条消息，判断要不要插一句、要不要把活接走，最常见的动作是”什么都不做”；它还会发只有一个人能看到的建议卡。它的主动停在对话层。

Super-agent 的主动是”任务式”：判断这是不是一个该开工的任务，开一张工单、派一个 Worker、跟到 PR。它的主动下沉到工单层。

差别最终落在授权上。Claude Tag 的授权按频道走——你被邀请进这个频道，它就有这个频道的权限，是静态的。Super-agent 的授权按请求走——每张工单一个授权，动作前还要再校验。所以前者是”我在这儿，有事叫我”，后者是”规则在这儿，我按规则开工”。

一个靠人盯，一个靠信任。

把镜头拉远

写到这儿，我脑子里冒出来的其实是白居易那句：乱花渐欲迷人眼，浅草才能没马蹄。

那一晚上我读到的几个版本快讯、三个”重磅”、两个”底层架构”，就是乱花。而真正能踩实的东西，数来数去只有两样：一套把并发、持久化、授权都做成规则的工程做法，和一组能复现的实验数字。

这也顺带解释了一件跟直觉相反的事。今年七月，上海科技大学基于 7.43 亿条招聘数据发过一份报告（科技日报的报道），结论是：新一线、二线城市的基础文职与内容岗，受冲击程度高于一线；一线反而因为高端线下服务、医疗这类岗位有所缓释。

报告里还有两个数字：收缩最集中在月薪 5000 到 8000、1 到 3 年经验的入门中端岗；约 18.6% 的岗位（约 2100 万）是任务重组出来的——既不是凭空消失，也不是凭空新增。

所以”岗位被替代”这件事，拆到任务粒度上会清楚很多：被拿走的是一批人用来练手的基础活，而不是职业本身。同一份报告里，客服在收缩，而资深 Java 工程师的架构设计和线上故障处置还在涨价。

三线城市”没什么感觉”，大概率也是这个道理：那里的产业结构 AI 暴露度本来就低。但那更像是滞后，不是屏障——大企业的岗位重写是渐变，小企业的工具替换是跳变，因为工具是打包好一次铺下去的。

如果你要读它

四件事，按性价比排序：

  1. 先读文档，按编号读。 docs/000 到 docs/007，作者刻意设计成每篇只依赖前面几篇，别从代码开始翻。
  2. 代码只看四五个文件。 007-architecture 里那张引擎部件表（Intake / Evals / Tickets / Assignments / Replies）是骨架；然后是 src/core/engine.ts（状态机）、src/policy.ts（授权闸门）、src/app/effects.ts（带退避的持久化副作用队列）、src/app/passes.ts（两秒一次成批处理）。剩下的两万多行不用看。
  3. 想跑起来，让 agent 陪你装。 仓库里的 SETUP.md 就是写给 coding agent 的：它一次问你一个问题，最后给你完整计划再执行。默认值很稳：独立 profile、独立的端口、accept 模式只记录不执行。有两个前提别省——用一个专门的 GitHub 账号（别用自己主号），只在测试仓库上跑。
  4. 想对比，读 Claude Tag 的文档。 大概半小时，你会看到同一个问题的另一种取舍。

下一步我想把上面那张”转换层”的表做实：从客服系统里那套分流规则出发，一步步改成 Agent 要的准入 + 授权 + 回放，写成一个能对照的映射表。
