# 写作手册：怎么写出吸引人的技术博客

> 私人手册（Hexo draft，不会被发布）。基于三组真实样本拆解：阮一峰《科技爱好者周刊》、酷壳陈皓《如何超过大多数人》《性能测试应该怎么做》、digoal《为什么 SVG 能走红》。

## 一、先想清楚：读者为什么要读你的文章

读者点开一篇文章的动机只有三种：

1. **有用**——我正被这个问题折磨，你告诉我怎么解决（digoal 的 SVG 文章、酷壳的性能测试）
2. **有趣**——这个标题/观点让我想看你怎么自圆其说（酷壳《如何超过大多数人》）
3. **有料**——帮我看完了看不懂/来不及看的东西（阮一峰的周刊）

写之前先问自己：这篇文章属于哪一种？三种都不沾的文章，写得再辛苦也不会有人看。

## 二、标题：决定 80% 的打开率

样本里的好标题公式：

| 公式 | 例子 | 来源 |
|------|------|------|
| 大问题 + 承诺 | 如何超过大多数人 | 酷壳 |
| 疑问句式 | 为什么 SVG 能走红？ | digoal |
| 具体数字承诺 | MySQL 性能优化的最佳 20+ 条经验 | 酷壳 |
| 反常识短语 | 禁止 issue，只用 PR | 阮一峰 |
| 场景 + 悬念 | 性能测试应该怎么做？ | 酷壳 |

反面教材：把文章目录当标题（"关于 XX 的若干思考与总结"）——没人对"总结"好奇，人们对"问题"和"反常识"好奇。

**自检**：把你的标题发给自己看，你会点开吗？如果答案是"这只是描述了内容"，重写。

## 三、开头三式（前 3 句定生死）

样本里的三种开头，按易学程度排序：

### 1. 痛点式（最推荐新手，digoal 招牌）

直接问读者有没有经历过那个痛苦场景：

> 你有没有遇到过这种情况？写一篇架构设计文章，想画个系统拓扑图，打开 PPT 折腾半小时，导出 PNG……第二天需求改了，图要改，重来一遍。

读者一看："对对对，我就是这样！"——注意力瞬间被抓住。**要点：场景必须具体到动作级**（"打开 PPT 折腾半小时"，不是"画图很麻烦"）。

### 2. 事件式（阮一峰招牌）

> 上周，PHP 框架 Laravel 宣布了一个新规定：禁止提交 issue，只能提交 Pull Request。

一句话交代完"谁在什么时候干了什么"。**要点：第一段就出现新闻或事实，背景介绍压到最短**。

### 3. 预期反转式（酷壳招牌，需要功力）

> 当你看到这篇文章的标题，你一定对这篇文章产生了巨大的兴趣……然而……当你看到我这样开篇时，你一定会觉得我马上就要有个转折，告诉你这是不可能的……然而，你错了。

先把读者心里的话说出来，再反转。**要点：节奏感强，适合观点输出，用多了会油**。

## 四、正文：递进结构，别平铺

三种样本的正文都是「递进」而不是「并列」：

- **digoal**：图片的原罪（问题）→ Mermaid 第一道曙光（不彻底的解法）→ SVG 真正的图文并茂（正解）→ 格式即生产力（升华）。每一节都在给下一节制造"但是/还不够"。
- **阮一峰**：抛出反直觉事实 → 读者心里冒出"这不合理吧" → 一二三拆解为什么合理 → 时代性收束（"AI 时代，提交 PR 几乎和提交 issue 一样简单"）。
- **酷壳**：观点毒辣直接，但每条都有具体支撑（"路透会用吞吐量乘以 66.7% 做软报警线"）。

**可执行模板**（适合 90% 的技术文章）：

```
痛点场景（你有没有遇到过…）
→ 问题命名（给这个痛点起个名字，如"图片的原罪"）
→ 常见解法及其不足（B 方案，但…）
→ 你的解法（为什么是 A，具体怎么做，代码/图）
→ 踩坑与细节（真实数据、真实案例）
→ 行动收尾（如果你也遇到，建议从…开始）
```

**关键技巧**：
- 每节结尾埋一个"钩子"引出下一节（"但 Mermaid 也有天花板"）
- 用设问推进："为什么是现在？""这意味着什么？"——设问是免费的节奏器
- 短段落，一段不超过 4 行；金句加粗，一篇文章 3-5 处，多了廉价

## 五、语言：向这三个样本学四件事

1. **用"你"**：三个样本全部高频用"你"——"你有没有遇到过""当你看到"。写作是和读者说话，不是发文件。
2. **动词具体**："打开 PPT 折腾半小时"好过"操作繁琐"；"图要改，重来一遍"好过"维护成本高"。
3. **敢下判断**：平均值是非常不靠谱的（酷壳）/ 这不是不是……而是（digoal："它的崛起，本质上是……"）。读者来看观点，不是来看"各有优劣"。
4. **比喻只用来解释机制**：像一根刺 / 外置大脑 / 压测思路——好的比喻帮读者理解抽象概念；形容词堆砌式的比喻是废话。

## 六、结尾：不要总结，要行动

- digoal 的结尾是三条"如果你……建议你……"——读者合上文章知道下一步干什么
- 酷壳的结尾是"（全文完）"——干脆
- 阮一峰的结尾是顺势给出一个更大的判断，让文章停在思考的延长线上

**禁**：结尾写"以上就是今天的分享，喜欢的话点个赞"（平台腔）；"由于水平有限，欢迎指正"（过度自谦，删掉，错了读者会说）。

## 七、发布前的自检清单

- [ ] 标题：我会点开吗？
- [ ] 前 3 句：是痛点/事件/反转之一吗？
- [ ] 正文：有递进吗？还是 ABC 三个点的平铺？
- [ ] 每段 ≤ 4 行？
- [ ] 有没有至少一处"只有我知道"的东西（真实数据、踩坑、内部视角）？——这是区分"网文"和"你的文章"的关键
- [ ] 结尾：读者知道下一步干什么吗？
- [ ] 读一遍，删掉所有"了""的""其实""非常"能删的

## 八、节奏建议（针对你的博客）

1. **第一批文章从 L1/L2 选题**（学习路径页里的 📋 节点）：AI 基础知识和开源项目解析最容易套"痛点式"开头——你转型时踩的坑就是读者的痛点
2. **一篇文章只解决一个问题**，想写的多了拆成系列（系列天然带来关注）
3. **先写 5 篇再改版式**：风格是写出来的，不是设计出来的；写满 5 篇后回看，自然知道该调什么
4. 每篇发布后记录：阅读来源、哪段被人引用/讨论——两周就能校准出你的读者要什么

## 九、金句速查（写卡的时候看）

- "写不清楚 = 没想清楚"
- "读者不欠你耐心，标题不勾人就走了"
- "具体，具体，再具体——数字、动作、场景"
- "一篇文章一个问题"
- "结尾让人带着行动离开"

## 十、AI 味自检（第一篇精读笔记返工的教训）

第一版《Agent 的能力边界，由 Harness 决定》被批"流水线、AI 味、没有看下去的欲望"。病灶清单：

1. **加粗泛滥**——几乎每段都有加粗金句，等于没有金句。全文加粗 ≤ 4 处，留给真正划线的地方
2. **小标题对仗工整**——"一个公式，两个层次"式的四字标题是 AI 的指纹。小标题要么口语化（"公式""判词""我的位置"），要么不用
3. **笔记腔开场**——"这是专题第一篇，写下我的理解"是说明文开头。要从"我"的处境切入（执念、误区、踩的坑），让读者跟着叙事走
4. **转述原文**——"原文里我最认同的一句判断"是读书报告。改成"我愿意称之为判词"这种带立场的引用
5. **每段等长、节奏均匀**——好的博客段落长短错落，一两句的短段是免费的强调
6. **信息压缩过度**——为了精炼把血肉删光，剩下的全是骨架（"知识点 A。知识点 B。"）。留呼吸感：一句闲笔、一个画面（"活在各自的玻璃房里"）
7. **把私人定位写进公开文章**——"我该占住什么位置"这类职业规划、自我表态是私人笔记的内容，公开博客是写给读者的。观点可以个人的，但不能是自我规划
8. **断言留余地**——"发展史就是……史"这种全称断言容易武断。用"我读出了一条线索""至少在……"收窄，读者可以反对你，但要先给人家站的地方

修正后的标准：读者能感觉到**屏幕后面有一个人**，而不是一个摘要引擎。
