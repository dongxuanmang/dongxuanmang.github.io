> 这篇不是读书笔记。[《深入理解 AI Agent》](https://github.com/bojieli/ai-agent-book)第 3 章把 ANN 索引的结论给全了，我把其中四个细节单独拎出来实现了一遍：中垂面为什么等价于"离谁更近"、层号公式到底在抽什么、边数为什么不会膨胀、以及分层究竟贡献了多少。上一篇[词有倒排，向量有图](/2026/09/28/agent-book-ch3-rag-retrieval/)画的是轮廓，这一篇是轮廓下面的砖。最后还补了对照组：精确 KNN 为什么做不到一个都不漏。

## 我能背出结论，却答不上"节点里存了什么"

读 RAG 那几节，我很快就能说出"树适合静态库、图适合动态库、两者都要重排序"。这套话术成立，所以我也就没再往下问。

直到有人问我：那棵树里的内部节点，到底存了什么？层号是怎么定的？

我一个都答不上来。能复述结论和知道机器怎么转，中间隔着一次自己动手。于是我写了几个脚本，把 ANN 索引的几个关键处从头实现了一遍。

四个直觉，三个被推翻，最后一个把我自己的结论也推翻了。

## 一、我以为那棵树是"基于余弦"设计的

ANNOY 是"基于树"的。既然整个检索都在比余弦，树大概是按余弦切分空间、加速查找的吧？

不是。它用的是**随机超平面**——随机挑两个点，取它们连线的中垂面切一刀，一路递归到叶子。整个过程跟余弦毫无关系，甚至不看数据分布。

那为什么这样切能加速？因为有一条初等几何事实：

> 两个点的中垂面，就是到这两点距离相等的点的集合。

于是判断一个新点该往哪边走，只需要算一次点积的符号。代数上四行就能证完：

```
|x-p1|² - |x-p2|² = -2 · n·(x - mid)     （n = p1-p2，mid = (p1+p2)/2）

⇒  n·(x-mid) ≥ 0  ⟺  |x-p1| ≤ |x-p2|
```

我拿两万个随机点验证了这条等价，两种判法（点积符号 vs 真算两个距离）不一致的有 0 个。

![中垂面：一条直线把平面分成"离 p1 近"和"离 p2 近"](/images/agent-book/ch3-ann-geometry.svg)

把三种结构摆在一起看：左图是 HNSW 的节点与边，中图是 ANNOY 的随机分割面，右图是 HNSW 的分层结果。

![两类 ANN 索引的构建结果：向量图、随机超平面、分层结构](/images/agent-book/ch3-ann-index.svg)

搞明白这一点之后，我觉得树的设计理解了。但我漏了一个更关键的问题：**树切得准不准，其实根本不重要**。

因为树只负责**路由**，不负责排序。它把查询送进一小片叶子就算完工，候选集最后还要用余弦精确算一遍。

这让我回头注意到一个之前完全没意识到的差异：

- ANNOY 的**近似**是"候选集里可能根本不含真近邻"——因为它分割时压根不看余弦；
- HNSW 的**近似**是"贪心游走可能从未走到真近邻"——但凡是走到的点，距离都是精确算的。

两者的距离计算都不近似。"近似"都发生在"有没有走到它"。

## 二、我以为稀疏和稠密是"静态"和"动态"

这个词我一开始是按"进化阶段"理解的：Word2Vec 是静态的，不够用，所以有了上下文感知；稀疏是老的，稠密是新的。

实际上这是**两根正交的轴**，被我压成了一根。

|  | 静态（每词一向量） | 动态（看上下文） |
|---|---|---|
| **稀疏** | BM25 / TF-IDF / 词袋 | SPLADE、BGE-M3 的 sparse 输出 |
| **稠密** | Word2Vec | BERT、BGE-M3 的 dense 输出 |

BM25 是稀疏的，但它属于静态那一侧，纯统计，没有任何神经网络。Word2Vec 是稠密的，但它也是静态的。

书里有个证据我一开始完全读漏了：BGE-M3 同时输出稠密、稀疏、多向量三种表示。一个模型同时给出两种"路线"，说明稀疏/稠密根本不是二选一的模型选项，而是两种表示形式。

那真正的界定标准是什么？零值比例只是表象。决定性的差异是**每一维有没有明确含义**：稀疏向量的每一维对应词表里的一个具体词，可枚举、可解释；稠密向量的每一维是人无法解释的，是模型学出来的。

## 三、我以为层号是某种复杂的打分

HNSW 给每个点随机分配层号，公式是：

```
lvl = floor( -ln(u) × mL )        u ~ Uniform(0,1)
mL  = 1 / ln(M)
```

两个参数、一个对数、一个取整。我背下来了，但完全不知道它在抽什么。

后来把 `mL` 代进去看了一眼：

```
lvl = floor( -ln(u) / ln(M) ) = floor( -log_M(u) )
```

`mL = 1/ln(M)` 的唯一作用就是**换底**。没有别的玄机。

换成 `-log_M(u)` 之后，`P(lvl ≥ k) = P(u ≤ M^-k) = M^-k`。这就是"连续掷出 k 次正面、每次概率 1/M"的概率。

所以这个公式等价于一句话：**反复掷一枚正面概率 1/M 的硬币，正面连续出现几次，层号就是几。**

我写了个动图把这个过程拆开。下面这张是公式版的示意——横轴取对数刻度后，`-log_M(u)` 是一条对角线，`floor()` 把它压成台阶，台阶就是层号：

![HNSW 层号公式的逐帧演示](/images/agent-book/ch3-hnsw-formula.gif)

掷硬币法和公式法各抽 20 万次，分布逐位重合：74.9% / 18.9% / 4.6% / 1.2% / 0.3%，对理论值 75% / 18.75% / 4.69% / 1.17% / 0.29%。

这时候我才算真的"看见了"这个公式，而不是记住它。

## 四、我以为分层一定更好——这里我把自己推翻了

前面的问题都还算温和，这一节是我翻车的地方。

HNSW 的核心卖点是"分层可导航小世界"。分层的道理听上去天经地义：上层节点稀疏，上层里的近邻在全局看来就相距很远，于是变成了长跳；查询从顶层入口一路贪心下降，先粗后细。

我还专门量了一遍各层的平均边长，数据非常漂亮：

```
层     节点数   边数    平均边长
L2     13      43     0.857
L1     74      271    0.540
L0     500     3625   0.403          （余弦距离，越大越远）
```

越往上边越长。到这里我以为结论已经坐实了：分层有用。

然后我做了个对照实验，把"层到底贡献了多少"单独拎出来——同一张图，查询时跳过上层，只在层 0 做同样的最佳优先搜索：

```
         A 分层查询    B 仅层0(同图)   C 扁平NSW+启发   C' 扁平NSW 无启发
ef=10    0.517       0.536         0.520          0.504
ef=20    0.668       0.683         0.687          0.646
ef=40    0.811       0.810         0.830          0.800
```

A 和 B 基本一样，而且**分层的下降路径平均多花 14 次距离计算**。A 和 C 相比，扁平的甚至略好。

分层的 recall 平均低 0.009，还更贵。

我第一版写的结论是"分层的 recall 明显更高"——数据出来是 0.478 对 0.480。那句话是我凭直觉写的，不是凭数据。

### 为什么分层在这里没用？

三个原因，缺一不可：

**一、我漏了论文里真正的那个设计。** HNSW 的邻居选择不是"取最近的 M 个"，而有一个多样性启发式：候选若"离某个已选邻居"比"离新点"还近，就丢弃。它强制邻居方向分散，上层才有真正的长跳。我把这一步省了，上层就退化成"同一邻域的子采样"，分层的意义被抽空。

实测：加上这个启发式，扁平 NSW 的 recall 平均提升 0.020——**比分层带来的差异还大**。

**二、规模不够。** 分层的理论收益是搜索复杂度从准线性降到 O(log N)，这是 N 到百万级以上才拉开差距的渐进性质。我只有 6000 个点、层 0 每点还有 16 条边，扁平图本来就够好走了。

**三、ef 太大。** 层 0 的最佳优先搜索是一个宽度为 ef 的波束搜索，ef≥10 时它会自己"漫"到目标邻域，从哪儿出发关系不大。

这件事给我的教训比结论本身重要：**分层是骨架，邻居选择启发式才是肌肉。** 论文里那些看起来次要的实现细节，往往才是性能的真正来源。

## 五、顺手记下的三笔账

这几个数字是这轮实验的副产品，但都挺反直觉。

**边数会不会膨胀？不会。** 每个点每层的度数有硬上限（层 0 是 2M，其余层是 M），一超就踢掉最远的。所以边数是 O(N·M)。实测固定 M=8：

```
N       总边数    边数/N   理论上界   实际/上界
200     1698     8.49     1,714     0.99
1000    8634     8.63     8,571     1.01
4000    34265    8.57     34,286    1.00
```

N 涨 20 倍，"边数/N" 从 8.49 到 8.57 几乎不动，实际值紧贴理论上界。

**HNSW 会漏，但漏的是"没走到"。** 600 个点、ef_search=20、取 top-10，300 个查询里 top-1 命中率 95.3%。我挑了一个漏掉的案例解剖：真第 1 名相似度 0.8790，HNSW 找到的第 1 名只有 0.5859——去查这个真第 1 名有没有被访问过，答案是**否，压根没走到**。不是算错了，是没走到。

**存超平面的内存开销比我以为的小。** 768 维、100 万文档，原始向量 3.07 GB，ANNOY 的超平面只要 31 MB，占 1%。倒是 HNSW 的层 0 邻接表要 128 MB——这才对上书里表 3-2 那句"ANNOY 内存低、HNSW 较高"。

## 查询到底交出一个 chunk，还是一批？

这是我最开始的问题，答案在最后才清楚。

HNSW 一次查询分三段，每段交出的数量完全不同：

{% mermaid %}
graph TD
    Q["查询向量 q"] --> D["下降阶段 L_top→L1<br/>每层只留 1 个点<br/>（路由，不产出结果）"]
    D --> L0["层 0 beam search<br/>宽度 ef_search<br/>留 10~200 个候选"]
    L0 --> K["截断取 top-k<br/>10~100 个"]
    K --> F["与稀疏结果融合 RRF<br/>~2×top_k"]
    F --> R["跨编码器重排<br/>取 3~10 个"]
    R --> P["塞进 prompt<br/>3~10 个 chunk"]
    style D fill:#f1f3f5,stroke:#adb5bd
    style P fill:#fff3cd,stroke:#b8860b
{% endmermaid %}

```
阶段                    批量（典型值）
HNSW 层 0 候选           ef_search = 10~200
稠密检索 top_k           10~100
稀疏检索 top_k           10~100
── 两路融合（RRF）──     ~2×top_k
跨编码器重排序           重排后取 3~10
塞进 prompt              3~10 个 chunk
```

只有下降阶段是"只留 1 个点"，但那是路由，不是结果。整条管道一路都是"一批"，因为早期就砍到 1 个，后面没有补救余地。

而 HNSW 本身**不做重排序**。它交出的候选已经按余弦排好了，但那只是向量相似度这个廉价信号。重排序用的是另一个贵得多的模型，把 query 和 chunk 拼在一起送进交叉编码器，能做词级交互。

## 有没有一个都不漏的办法？

前面五节讲的全是 ANN。但"近似"这个词，只有在有精确对照时才成立。所以最后把对照组补上。

先把两个词分清：

| | 是什么 | 保证 |
|---|---|---|
| **KNN** | **问题**：找离 q 最近的 k 个点 | **一个都不许漏** |
| **ANN** | **解法**：快速找到"大概是最近的" | 允许漏，用召回率衡量 |

所以 ANN 不是 KNN 的替代品，是它的妥协解法。

精确求解 KNN 有几条经典路线：暴力扫描、KD 树、Ball 树。我把它们都实现了一遍，第一件事是验证结果完全一致——这是 exact 的定义：

```
暴力 vs KD 树 ：50/50 个查询的 top-10 完全一致
暴力 vs Ball树：50/50 个查询的 top-10 完全一致
```

对照一下：前面测 HNSW，600 个点时 top-1 就只有 95% 命中率。

后两种树的加速全部来自同一个东西——**三角不等式剪枝**。树结构想跳过一整棵子树，必须先证明"那棵子树里不可能有比当前第 k 名更近的点"：

```
d(q, x) ≥ d(q, c) - d(c, x) ≥ d(q, c) - r
```

`c` 是子树包住的球的球心，`r` 是半径。q 到球心的距离减去半径，就是 q 到球面的最短可能距离——它若已经比当前第 k 名还远，整棵子树可以跳过。

KD 树是它的特例：切分面对应一个"无限薄的超平面"，用「q 到切分面的垂直距离」代替 `d(q,c) - r`。两者其实是同一个条件的两种写法。

那为什么不一直用精确方法？因为这条路有硬天花板。同样 N=3000，扫描不同维度：

```
维度   暴力       KD树      KD 剪枝率   Ball树     Ball 剪枝率
2     360000   3019      99.2%      5292      98.5%
4     360000   51237     85.8%      349800    2.8%
8     360000   327609    9.0%       427904    -18.9%
16    360000   360000    0.0%       427680    -18.8%
32    360000   360000    0.0%       427920    -18.9%
128   360000   360000    0.0%       426240    -18.4%
768   360000   360000    0.0%       426960    -18.6%
```

![维数灾难：剪枝率在 16 维归零，而最近/最远距离比一路爬到 0.89](/images/agent-book/ch3-knn-curse.svg)

柱子在 16 维掉到 0——索引白建了。橙色线一路爬到 0.89：当"最近的"和"最远的"几乎一样远，任何剪枝都无从下手。

Ball 树的负数是真实结果，不是 bug：我的向量都归一化在单位球面上（真实 RAG 正是这个形态），超球之间重叠严重，本来就难剪；而它每访问一个内部节点要额外算两次球心距离，剪不掉东西时这个固定开销就显露出来了。

**这是维数灾难，不是工程没优化好。** KD 树、Ball 树、VP 树、cover tree，全都死在同一堵墙上。

## 那精确 KNN 还有用吗

有，而且不少场景必须用。

**小库中库直接暴力算。** 真实 RAG 里 faiss 的 `IndexFlatIP` 就是暴力扫描。几十万向量以内，很多系统根本不上 ANN——省掉一堆调参和召回率的不确定性。

**需要 100% 召回。** 法规、医疗、合规检索漏一条可能就是事故，95% 召回不可接受。

**它是 ANN 的标尺。** 调 `ef_search` 时拿什么判断召回够不够？拿精确 KNN 当真值。我前面测 HNSW 的 recall@10，基准就是暴力扫描。

**重排序本身就是暴力 KNN。** 粗召回 100 个候选后对这 100 个精确算距离，N 从百万变成了 100。

| 场景 | 推荐方案 | 理由 |
|---|---|---|
| < 10 万向量 | 暴力 / IndexFlat | 精确、零调参，速度够 |
| 10 万 ~ 100 万 | ANN + 精确重排 | 粗排省时间，精排保质量 |
| > 100 万 或高 QPS | ANN（HNSW/IVF） | 只能近似，靠调 ef 控召回 |
| 维度 < 20 | KD 树 | 剪枝有效，精确且快 |
| 维度 128+ | ANN | 树结构已退化，别浪费 |
| 调 ANN 参数时 | 暴力当基准 | 没有真值就不知道召回多少 |

> 最后一行最容易被忽略：**没有精确基准，你说不出自己的近似算法到底漏了多少。**

## 如果你也在读这一章

三条建议，按我的踩坑顺序：

**先把结论放下，去实现一个最小的。** 我用两百行不到的 Python 把 ANNOY 和 HNSW 都写了一遍。写不出来的地方，就是没懂的地方——我第一次实现 `_search_layer` 时堆的符号写反了，查询直接返回余弦值 1.0655（归一化向量不可能超过 1），这种错误只有跑起来才会暴露。

**任何一个"某设计一定更好"的说法，先在自己手上量一遍。** 我为这句话付出了代价：第一版分层结论是错的。现在脚本里所有结论都从实测数字生成，就是为了防止叙述和数据打架。

**别把实现细节当次要。** 分层是显眼的设计，邻居选择启发式是藏在论文 Algorithm 4 里的一页。但后者才是我实测中真正起作用的那一个。
